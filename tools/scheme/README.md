# Генератор моделей

Страница `/3d-gen/` в лейауте СТРОЙГАЗ: STEP, STL, OBJ или GLB → модель (студийный рендер или трассировка лучей) → контур (растр G-буфера + рёбра модели) → PNG. В браузере работают three.js, OpenCascade / WebAssembly и Web Worker. Сервера конвертации, CDN и отправки файла нет. Исходный проект `/home/foxqa/Projects/outline-lab` не изменяется и больше не нужен для сборки сайта.

## Структура

- `src/scheme.njk` — вся разметка, базовый лейаут, noindex; страница исключена из коллекций и sitemap, в навигацию не добавлена.
- `src/assets/style.css`, блок `.scheme-*` — оформление через IDS и компоненты сайта. Vendor IDS не меняется. Общего range-компонента в подключённой IDS нет (есть только специализированный для gen-cover demo), поэтому нативные range стилизованы в духе playground: трек 2 px цвета `--ids__border`, заполненная часть (переменная `--scheme-fill` из `main.ts`, в Firefox — `::-moz-range-progress`) и круглый бегунок 11 px цвета текста. Сетка настроек — 0,8 от текста приложения; на касании (`< 1100px` или `pointer: coarse`) ряды и кнопки не ниже 32 px. Цвета «Линия» и «Фон» — чипы 16 × 16 (`.scheme-swatch`), нативный input внутри невидим.
- `tools/scheme/src/` — TypeScript, просмотр, контур, пресеты, STEP-разбиение и workers. `mesh.worker.ts` читает сетки штатными загрузчиками three.js (STLLoader, OBJLoader, GLTFLoader) без OpenCascade. `edges.ts` — рёбра модели и нормали с изломом (считаются в workers), `outline-pass.ts` — проход контура, `shading-pass.ts` и `studio.ts` — студийный рендер режима «Модель», `tracer.ts` — трассировка лучей (отдельный чанк, грузится при первом выборе режима «Трассировка»).
- `tools/scheme/examples/dosing.preset.json` — ракурс дозирования: зеркало X, 350°.
- `tools/scheme/tests/` — тесты проекции, пресетов, STEP-графа, форматов сеток и проверка в Chrome.
- `src/assets/scheme/` — результат Vite, **не коммитится**. Eleventy копирует его вместе с остальными `src/assets`.

## Запуск и сборка

Один `package.json` и lock-файл в корне сайта. Node.js ≥ 22.12 (CI — Node 24).

```bash
npm ci
npm run build                 # TypeScript → Vite → Eleventy
npm run build -- --pathprefix=/stroigaz/  # та же сборка для GitHub Pages
npm run dev                   # первая сборка приложения → Eleventy на :8080
```

При работающем `stroygaz-eleventy.service` достаточно `npm run build:scheme`, затем открыть `http://localhost:8080/3d-gen/`. Для работы над TypeScript запустите во втором терминале:

```bash
npm run dev:scheme            # vite build --watch, пишет в src/assets/scheme/
```

Eleventy (`npx eleventy --serve --port 8080`, в том числе существующий systemd user unit) следит за `src/assets/` и подхватывает пересборку. После чистого клонирования перед прямым `npx eleventy` нужна первая `npm run build:scheme`; обычный `npm run build` делает всё сам. HTML/стили редактируются как остальные страницы сайта.

В `.github/workflows/pages.yml`: `npm ci` → `npm run build:scheme` → `npx eleventy --pathprefix=…` → публикация `_site`. Vite имеет `base: './'`; точка входа — стабильный `assets/scheme/scheme.js`, пути к вложенным workers и WASM вычисляются относительно модуля (`import.meta.url`). Префикс ссылки на точку входа добавляет HtmlBasePlugin Eleventy. Поддерживается обычный статический HTTP(S), без COOP/COEP и backend. `file://` не подходит.

## Форматы

| Формат | Чем читается | Оси | Нормали |
|---|---|---|---|
| `.step`, `.stp` | OpenCascade в `import.worker.ts` → `step.worker.ts` | как в STEP (Z вверх, мм) | из BREP |
| `.stl` (binary и ascii) | STLLoader в `mesh.worker.ts` | как есть: Компас и другие CAD пишут STL в осях STEP, поворота нет | всегда пересчитываются из порядка вершин, с изломом (см. ниже); нормали из файла не используются (часто нулевые) |
| `.obj` | OBJLoader | как есть: у формата нет оси «вверх», CAD-экспорт сохраняет Z вверх. Из Blender экспортируйте с Up = Z | `vn` из файла, иначе с изломом. MTL не читается, цвет серый |
| `.glb`, `.gltf` | GLTFLoader | по спецификации Y вверх, метры. Поворот +90° вокруг X, `(x, y, z) → (x, −z, y)` — без зеркала, затем ×1000 в мм. Фронт glTF (+Z) становится −Y STEP | из файла, иначе с изломом. Цвет — `baseColorFactor` |

Сетка приходит в той же структуре `Part[]` / `AssemblyNode`, что и тесселяция STEP: неиндексированные треугольники, трансформации узлов запечены, по одной детали на меш (STL — одна деталь). Нормали «с изломом»: вершины сшиваются по точным координатам, нормаль усредняется (с весом по углу при вершине) только по соседним граням, отличающимся меньше чем на 40° (`SMOOTH_ANGLE`), — фасеты цилиндра не дают ложных складок, настоящие рёбра остаются резкими. CAD-рёбер у сетки нет, поэтому рёбра берутся из самой сетки — см. «Как строится контур». Текстуры glTF не загружаются; `.gltf` должен содержать данные внутри (data URI) — внешние `.bin`, Draco, Meshopt и KTX2 не поддерживаются, лучше сохранять `.glb`. OpenCascade и WASM для сеток не загружаются (воркер около 260 КБ).

Проверено на КНС хозяйственно-бытовых сточных вод из Компаса: бинарный STL 45,2 МиБ, 948 852 треугольника — до готовой модели около 0,7 с (из них рёбра и нормали ≈ 0,45 с в воркере), геометрия ≈ 100 МиБ, из них рёбра ≈ 25 МиБ (921 707 отрезков от 1°), headless Chrome.

## Режим «Модель»: студийный рендер

Картинка режима «Модель» — заготовка для ИИ-генератора фотореалистичного рендера, поэтому важны читаемая форма, объём и мелкие детали, а не цвет. Падающей тени на пол нет: ни плоскости-«ловца теней», ни контактной тени под основанием, фон остаётся чистым цветом «Фон». Объём дают окружение, свет, ambient occlusion и тени модели на саму себя. Проход `shading-pass.ts`:

1. **Окружение** (`studio.ts`) — встроенное нейтральное студийное HDR, считается в коде (equirect 1024×512, без загрузок): серый купол (зенит 0,6, горизонт 0,36, низ 0,12), ключевой софтбокс слева-сверху относительно камеры (азимут камеры −55°, высота 58°), слабый заполняющий справа и длинная контровая полоса сзади — блики на обечайках, трубах и кромках крышек. Растеризация не умеет затенять окружение, поэтому в её карте ключа и заполняющего нет: вместо них направленные источники с той же освещённостью (ключ — с картой теней), а окружение three.js сам переводит в PMREM. Трассировщик видит полную карту и даёт мягкие тени от софтбоксов.
2. **Материал** — `MeshStandardMaterial`: светлый нейтральный серый (линейный 0,42), metalness 0,2, roughness 0,5. Цвета деталей из STEP/GLB сохраняются, но приглушены: наполовину обесцвечены и на 45 % смешаны с серым.
3. **Тени** — только самозатенение: ключ с картой теней PCF 4096² (2048², если `MAX_TEXTURE_SIZE` < 8192), радиус 2,5 текселя, фрустум — сфера модели (полудиагональ bbox), `normalBias` ≈ 3 текселя. Карта перерисовывается при загрузке и смене ракурса, не каждый кадр.
4. **Ambient occlusion** — `GTAOPass` из `three/examples` (ортокамера поддерживается), 16 сэмплов + пуассоновский денойз. Радиус задаётся в пикселях кадра 1× (по умолчанию 12 px — около 200 мм на КНС при масштабе 1×) и переводится в единицы модели, поэтому экран, 1×/2×/4× выглядят одинаково и единицы файла не важны. Фон глубины не имеет и не темнеет. Денойз — 24 сэмпла в 3 кольцах, радиус 1,5 px кадра 1× (2–8 px буфера), **с одним фиксированным поворотом ядра** вместо случайного на каждый пиксель (штатный `pdNoiseTexture` three.js заменён на текстуру 1 × 1). Прежний денойз (радиус 4 px × масштаб, случайный поворот) превращал крутой градиент AO у контакта — обечайка КНС на опорной плите — в тёмное зерно по нижнему ободу; сырая карта GTAO там гладкая, тени и acne к этому отношения не имеют (с затенением 0 зерна нет). Меньший радиус фиксированного ядра ещё и не даёт «двойного кольца» у стыка. Это меняет PNG режима «Модель» (не «Контур»).
5. **Рёбра на модели** («shaded with edges») — те же рёбра и та же проверка видимости по глубине, что у контура (`featureEdgeMaterial` из `outline-pass.ts`), в маску 1 px с MSAA; в композите расширяются до 0,75 px кадра 1× (1,5 px в 2×, 3 px в 4×, на экране — × ширина буфера / 760), цвет `#1b2024`, непрозрачность 0,55. Для сеток действует порог нормалей контура.
6. **Композит** — ACES Filmic (формула three.js) только по модели, AO, затем модель поверх фона по альфе, рёбра, sRGB. Фон не проходит через тон-маппинг: белый остаётся 255.

Beauty рисуется в half-float цель с MSAA 4×, нормали сеток — сглаженные до 40° (`SMOOTH_ANGLE`), цилиндры без фасеток. Режим «Контур» от всего этого не зависит: другие материалы через `overrideMaterial`, своя камера и свои цели; PNG контура до и после этой работы совпадают попиксельно на КНС и дозировании (1× и 2×).

Настройки — раздел «Модель»: «Затенение» (0–2: до 1 подмешивает AO, выше — углубляет, 0 выключает), «Радиус» (2–40 px) и «Рёбра на модели» (по умолчанию вкл.). В пресете они лежат в блоке `shading`.

### Трассировка лучей

Третий режим переключателя на холсте «Модель / Контур / Трассировка»: прогрессивный path tracing через [`three-gpu-pathtracer`](https://github.com/gkjohnson/three-gpu-pathtracer) 0.0.28 (`WebGLPathTracer`, WebGL 2) с BVH из `three-mesh-bvh`, построенным в отдельном worker. Модуль импортируется динамически (чанк ≈ 160 КБ + worker BVH ≈ 170 КБ) только при выборе режима; страница и обычный рендер его не грузят. Используются глубокие импорты `src/core/WebGLPathTracer.js` и `src/workers/GenerateMeshBVHWorker.js`, чтобы не тянуть индекс пакета с xatlas/WASM.

- Та же ортокамера изометрии (библиотека поддерживает ортографическую проекцию: `CAMERA_TYPE 1`), те же материалы, полное студийное окружение, 5 отражений, MIS, `filterGlossyFactor` 0,5. Направленные источники растра в трассировку не идут: ключ и заполняющий — софтбоксы окружения.
- Фон трассировщика чёрный, поэтому радианс модели предумножен на покрытие; покрытие и рёбра берутся из растрового прохода в том же разрешении, ACES и фон — как в студийном рендере.
- Кадр 1520 × 1000 (2×). Остановка повторным кликом по активному сегменту «Трассировка» (пока идёт расчёт, подпись пульсирует), уходом в другой режим, после 300 сэмплов или через 60 с (`TRACE_LIMIT` в `settings.ts`). Прогресс — на плашке внизу холста (`#stage-note`) и в статусе внутри «Журнал и диагностика». На GPU сэмпл — один полный кадр за `requestAnimationFrame`, на SwiftShader/llvmpipe (определяется по `WEBGL_debug_renderer_info`) — тайлы 8 × 8, чтобы остановка отвечала. Без WebGL 2 с `EXT_color_buffer_float` сегмент неактивен, причина — в подсказке.
- PNG 1× и 2× берут готовый результат (1× — уменьшение), имя файла `*.traced.Nx.png`; для 4× трассировка повторяется в 3040 × 2000 с теми же лимитами и сохраняется по окончании.
- Поворот, зеркало, масштаб, сдвиг, смена кадра экспорта (если масштаб или сдвиг не по умолчанию), импорт пресета, настройки раздела «Модель» и порог нормалей сбрасывают трассировку: холст показывает обычный рендер модели, клик по «Трассировка» считает заново. Уход в «Модель» или «Контур» останавливает расчёт: готовый результат показывается снова при возврате, прерванный считается заново. PNG в режиме «Трассировка» без результата сначала трассирует кадр. Открытие новой модели возвращает режим «Модель».
- `WebGLPathTracer` помечен в 0.0.28 как устаревший в пользу `WebGPUPathTracer` (предупреждение в консоли). Переход на WebGPU потребовал бы WebGPU-рендера всей страницы; пока WebGL-версия работает.

## Как строится контур

Модель рисуется в G-буфер 4× (3040×2000): нормали (RGB), номер детали (A) и глубина. Линии двух весов, как в сборочных инструкциях: **силуэт** — внешний контур деталей — и тонкие **рёбра** внутри них, с **зазором** (halo) там, где контур проходит перед дальней геометрией. Проход `outline-pass.ts`:

1. **Рёбра модели** (`edges.ts`, считаются в workers при загрузке) — точные 3-D отрезки рисуются линиями 1 px поверх G-буфера с проверкой видимости: отрезок виден, если его глубина не дальше видимой поверхности больше чем на 1 px высокого разрешения плюс локальный наклон глубины (у вогнутого ребра пиксель берёт глубину соседней грани).
   - **STEP:** все границы между BREP-гранями (CAD-рёбра, как в `scripts/anatomy/step-outline.py`), включая касательные. Диагонали тесселяции и швы периодических поверхностей внутри одной грани не рисуются. Свободные кромки рисуются всегда. От ползунков не зависят.
   - **STL / OBJ / glTF:** ребро между двумя треугольниками рисуется, если угол между ними не меньше угла порога нормалей (`2·asin(t/2)`: 0,55 ≈ 32°, 0,32 ≈ 18°). Открытые и неманифолдные рёбра (больше двух граней) рисуются всегда.
2. **Классификация.** Каждый пиксель сравнивается с четырьмя соседями (глубина с поправкой на касательную плоскость, чтобы наклонная грань не давала полосу; нормали; номер детали) и попадает в однопиксельные «ядра» трёх классов:
   - **силуэт** — ближняя сторона: край модели на фоне; уступ глубины на другую деталь; глубокий уступ (больше 4 порогов глубины, `HALO_DEPTH_FACTOR`) внутри детали; граница двух деталей без уступа (одна сторона, по номеру);
   - **ребро** — линия из п. 1, излом нормалей больше порога, мелкий уступ внутри одной детали (рёбра охлаждения мотора, канавки бака, рамка люка);
   - **дальняя сторона** глубокого уступа — то, перед чем проходит силуэт.
3. **Толщина и зазор.** Точное евклидово расстояние до ближайшего ядра каждого класса считается в два разделимых прохода (по строке, затем по столбцу в итоговом проходе), без квадратного цикла. Силуэт и рёбра получают свой радиус с мягким краем в 1 px. Рёбра на дальней стороне (пиксель ближе к ядру дальней стороны, чем к ядру силуэта) стираются на «Зазор» дальше края силуэта; ближняя деталь не затрагивается. Касание без глубокого уступа (болт на фланце, рамка на крышке) зазора не даёт — ребро упирается в контур, а не превращается в пунктир.
4. PNG 4× — G-буфер 3040×2000 как есть, 1× и 2× уменьшаются `drawImage` с высоким качеством. На экране контур рисуется в отдельную цель не меньше 4× (больше — если буфер холста шире 3040 px) и уменьшается до размера буфера холста шейдером `Downsample` (усреднение по площади, дробные веса на границах пикселя) — экранный аналог `drawImage`. PNG контура после переноса на экранный буфер совпадают с прежними попиксельно (КНС и дозирование, 1×/2×/4×).

**Номер детали** — 8 бит в альфе нормалей, без отдельного буфера: униформа на каждый draw call (`onBeforeRender`), деталь = меш (STEP — BREP-тело, glTF — меш, OBJ — объект). Номера последовательные, `index % 255 + 1`: соседи по сборке различаются, совпадают только детали через 255 — тогда их стык без уступа остаётся тонким. STL — одна деталь, у сетки толстый контур только по глубине. Стоимость на дозировании (1484 детали) неотличима от шума: весь проход контура на GPU — около 3–4 мс.

Время одного кадра контура (headless Chrome, медиана 7 замеров): дозирование — SwiftShader 315 → 363 мс, GPU (`--use-angle=gl`, RTX 5080) 6 → 3 мс; КНС — SwiftShader 276 → 317 мс, GPU ≈ 1,5 мс. Стоит поиск расстояний: радиус силуэта плюс зазор (по умолчанию 11 px высокого разрешения в каждую сторону) в двух проходах вместо 2 × 6 px раньше; толстый силуэт и широкий зазор с ползунков удлиняют оба цикла.

Почему не хватало одного растрового прохода (КНС, 948 852 треугольника, 3,1 × 3,2 × 7,2 м): пиксель 1× ≈ 17,6 мм модели, прежний порог глубины ≈ 12 мм (0,7 px), новый ≈ 27 мм (1,5 px) — дело было не в нормировке порога. Стык обечаек, накладка шва, рамка люка и головки крепежа меньше одного пикселя по глубине и почти не меняют нормаль, поэтому в контур попадали только отдельные точки (где нормаль крепежа отличалась). Гранные нормали на плотной сетке вдобавок давали серые штрихи на изгибах труб. Уменьшение разрешения было вторичным: на 4× крепёж уже был точками. В STEP то же происходило с канавками и рёбрами крышек баков — они выходили рваными серыми штрихами.

## Чёткость на экране

Холст на странице занимает всю ширину колонки (≈ 1090 CSS px при окне 1440), на HiDPI — вдвое больше физических пикселей. Раньше «Модель» рендерилась в 760 × 500 × min(DPR, 2) = 1520 × 1000 и растягивалась CSS до 2185 px (×1,44, отсюда мыло), а «Контур» — в 3040 × 2000 и сжимался браузером без качественного фильтра. Теперь буфер холста — его размер на экране: `ResizeObserver` (`device-pixel-content-box`, где браузер его даёт; иначе CSS-ширина × `devicePixelRatio`, плюс `matchMedia` на смену DPR) задаёт ширину буфера, высота — по 760 : 500, не больше `MAX_DISPLAY_WIDTH` = 4096 px. Композиция не меняется: камера, вписывание и кадр остаются в единицах кадра 760 × 500, меняется только число пикселей. «Модель» рисуется прямо в этот размер (масштаб = ширина буфера / 760, дробный), «Контур» — с суперсэмплингом, см. п. 4 выше. Экспорт PNG — по-прежнему ровно 760 × 500 × 1/2/4. Толщины линий, зазор, порог глубины, рёбра на модели, радиус AO и денойза заданы в пикселях кадра 1× и умножаются на масштаб буфера, поэтому экран и экспорт выглядят одинаково. Headless Chrome с эмулированным `deviceScaleFactor` отдаёт в `devicePixelContentBoxSize` CSS-пиксели — такое значение отбрасывается, если расходится с CSS × DPR больше чем на 2 px.

Цена: на DPR 2 и окне 1440 «Модель» рисует 2185 × 1438 вместо 1520 × 1000 (≈ 2× пикселей, MSAA half-float ≈ 100 МиБ); на 4K-мониторе с DPR 3 — до 4096 × 2695 (≈ 0,4 ГиБ). Замеры кадра ниже сделаны для 760 × 500 / 2× и не переснимались.

## Масштаб и сдвиг

- **Колёсико** над холстом — масштаб к точке под курсором (×1,16 за щелчок 100 px; жест щипка на тачпаде приходит как ctrl + колёсико). Пока модель не загружена, колёсико прокручивает страницу; с моделью — `preventDefault`.
- **Ползунок «Масштаб»** в столбце «Ракурс» — 0,5–6× относительно вписанного кадра, логарифмическая шкала, значение округляется до 0,05; приближает к центру кадра.
- **Сдвиг** — перетаскивание с Shift, средней или правой кнопкой (контекстное меню над моделью отключено). Обычное перетаскивание — поворот вокруг Z, клик без движения — имя детали.
- **Touch**: один палец — поворот, два — масштаб щипком и сдвиг. С загруженной моделью у холста `touch-action: none`, страница прокручивается за его пределами.
- **«Вписать»** и **двойной клик** — масштаб 1, центр.

В пресете — блок `view`: `zoom` (0,5–6), `panX`, `panY` — смещение центра кадра от центра вписанного кадра в долях его ширины / высоты (вправо / вниз, ±0,5 — до края вписанного кадра, дальше не уводится). Пресеты без `view` (и с частью полей) импортируются как вписанный кадр. Поворот меняет вписанный кадр, `view` остаётся относительным к нему. Камера пересчитывается без обхода вершин: проекция и карта теней зависят только от поворота и зеркала. Экспорт PNG и трассировка берут тот же кадр, что на экране.

Пороги и толщины привязаны к **кадру**, а не к модели: порог глубины — доля ширины кадра (≈ 1,5 px), линии и зазор — пиксели кадра 1×, радиус AO — 12 px кадра. На зуме 3× они те же на экране, а в единицах модели втрое меньше: проявляются мелкие уступы и складки, которых при 1× не видно, AO у стыков уже (≈ 70 мм вместо 200 на КНС). Это сделано сознательно — схема выглядит одинаково при любом зуме. Нужен прежний «модельный» охват AO — увеличьте «Радиус» в zoom раз (до 40 px).

**Кадр экспорта** — переключатель в столбце «Экспорт»: «Вся модель» (по умолчанию) или «Как на экране». «Вся модель» рендерит PNG 1×/2×/4× и трассировку во вписанном кадре 760 × 500 — масштаб 1, сдвиг 0, текущие поворот и зеркало (`exportFrame` в `settings.ts`); камера экрана на время PNG переставляется и возвращается, вид на холсте не меняется. Трассировка при зуме ≠ 1 считается со своей камерой, и холст показывает трассируемый кадр (в статусе — «вся модель»); любое изменение масштаба или сдвига возвращает обычный вид. «Как на экране» — кадр с масштабом и сдвигом, как раньше. В пресете — блок `export: { frame: "model" | "screen", transparent }`, пресеты без него импортируются как «Вся модель» с прозрачным фоном.

**Прозрачный фон** — чекбокс в столбце «Контур» в строке с «Линия» и «Фон», по умолчанию включён (`export.transparent`, старые пресеты — `true`). Касается только PNG: на экране холст остаётся цвета «Фон», имя файла не меняется. Холст WebGL — `alpha: true, premultipliedAlpha: true`; экран всегда пишет альфу 1, экспорт с чекбоксом — премультиплицированные цвет и альфу, `drawImage` усредняет при уменьшении 4× → 1×/2× тоже премультиплицированные значения, PNG сохраняется с прямой альфой. «Контур»: цвет линии × покрытие штриха, альфа = покрытие (без смешивания с «Фоном» — у края линии нет светлой каймы). «Модель»: альфа = покрытие beauty (MSAA), AO умножает только модель, рёбра на модели накладываются оператором over (линия у силуэта может выйти на полпикселя за модель), sRGB считается от непремультиплицированного цвета. «Трассировка»: фон трассировщика чёрный, альфа — покрытие растрового прохода в том же разрешении, радианс после ACES премультиплицирован им же; окружение в кадр не попадает. Без чекбокса — как раньше, по цвету «Фон».

Ограничения: карта теней ключа (4096², фрустум — сфера модели) от зума не зависит, на 4–6× мягкий край тени шире пикселя и заметнее; масштаб меньше 1 оставляет модель маленькой в кадре с полями; сдвиг не дальше края вписанного кадра.

## Поведение и ограничения

Defaults: поворот 0°, без зеркала; порог глубины 0,002 — **доля ширины кадра** (≈ 1,5 px при 760×500; кадр вписан по проекции модели, поэтому порог не зависит от единиц и размера модели; раньше это была доля глубины сцены), порог нормалей 0,55 (≈ 32°, как crease angle Python-конвейера; было 0,32), силуэт 2 px, рёбра 1 px, зазор 1,5 px (по референсу IKEA: контур вдвое толще внутренних линий), линия `#383e43`, фон `#ffffff`. Зазор 0 выключает ореол. Порог глубины ниже ≈ 0,001 даёт серые штрихи у силуэтов цилиндров сетки — рёбра модели уже рисуют мелочь, опускать его не нужно. PNG: 760×500, 1520×1000, 3040×2000. Отмена останавливает workers.

Допуски тесселяции STEP в интерфейсе не настраиваются: они зашиты константой `TESSELLATION` в `settings.ts` — 0,8 мм (абсолютный линейный) и 0,5 рад. Для STL/OBJ/GLB они не применяются: сетка уже состоит из треугольников.

Пресет JSON (`version: 1`) хранит ракурс (поворот, зеркало, блок `view` — масштаб и сдвиг, см. выше), настройки контура (`silhouetteWidth` 0,25–6, `edgeWidth` 0,25–3, `haloGap` 0–3 px) и блок `shading` режима «Модель» (`edges` — рёбра на модели, `occlusion` 0–2, `occlusionRadius` 2–40 px), без модели и без допусков. Пресеты без `shading` (и с частью его полей) импортируются, недостающее берётся по умолчанию; при экспорте блок пишется целиком. Старые пресеты с полем `tessellation` импортируются без ошибки, поле игнорируется и при экспорте не записывается. Старое единое `lineWidth` становится толщиной рёбер, силуэт — вдвое толще, зазор — по умолчанию; при экспорте пишутся новые поля.

- Вход до **384 МиБ**, меш до **5 млн треугольников / 512 МиБ** (для сеток тоже), таймаут **8 минут**; это защитные ограничения, не гарантия для любого файла такого размера. WASM-куча одного OCCT ограничена 2 ГиБ. Большие STEP делятся по независимым BREP-телам, не по произвольным кускам текста.
- В исходной лаборатории подтверждены дозирование (103,9 МиБ) и CIP (142,8 МиБ). **Обратный осмос (336,6 МиБ) не поддержан**: фрагмент 33/43 дал пустую тесселяцию. Причина не установлена; это не подтверждённое исчерпание памяти. Неполную модель приложение не показывает. Перенос на сайт не исправляет этот случай.
- WebGL 2 обязателен; крупные сборки не рассчитаны на малую память мобильных устройств. На 390 px проверяется вёрстка, не производительность телефона. Safari отдельно не проверялся.
- Контур растровый по тесселяции плюс рёбра модели с проверкой видимости по z-буферу, не точный CAD HLR/SVG и без векторизации. Скрытых штриховых линий, автоматического Y-up и серверного fallback нет.
- Рёбра сетки зависят от экспорта: у STL нет CAD-топологии, гладкие переходы (скругления, канавки без излома ≥ порога) рисуются только силуэтом. Мелкий крепёж (меньше ~2 px) остаётся маленьким замкнутым контуром или точкой — в 1× это его реальный размер; соседние параллельные кромки (фаски, листовые швы) сливаются в двойную линию. Очень плотные узлы (рёбра охлаждения моторов насосов) в 1× остаются тёмным пятном: мелкие уступы там уже тонкие, но их больше, чем пикселей.
- Трассировка: на КНС и дозировании проверена на RTX 5080. Память — сцена, склеенная в одну геометрию, плюс BVH и float-текстуры атрибутов: порядка сотен МиБ на 1,6 млн треугольников; на слабых GPU возможна потеря контекста WebGL. Текстуры и прозрачность CAD-цветов не используются.
- WASM загружается при первом открытии STEP (не сетки): около 7,6 МБ без HTTP-сжатия; весь JS/WASM-бандл — около 8,3 МБ, модуль трассировки — ещё ≈ 0,4 МБ по кнопке. При обновлении зависимостей размеры могут меняться.
